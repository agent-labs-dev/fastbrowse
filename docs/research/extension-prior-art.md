# Prior art: driving a signed-in Chrome through an extension

Research for #785, part of #784, feeding the extension backend in #630. For Claude in Chrome, the Codex (ChatGPT) Chrome extension, Playwright MCP `--extension`, browser-use and Stagehand, it covers four things: which extension APIs carry the actions, how the agent process reaches the extension, what the user sees, and how each is installed. The CDP limits of `chrome.debugger` are covered in [`extension-cdp-coverage.md`](extension-cdp-coverage.md) and are not repeated here.

## Two Chrome facts every design inherits

1. **The debugger infobar.** Every `chrome.debugger.attach` shows the infobar `"<extension name>" started debugging this browser` (`IDS_DEV_TOOLS_INFOBAR_LABEL`, `generated_resources.grd:4779`). `ExtensionDevToolsClientHost::Attach` (`debugger_api.cc:715-734`) suppresses it only when Chrome runs with `--silent-debugger-extension-api` or when the extension is installed by enterprise policy (`Manifest::IsPolicyLocation`). After the last client detaches, the infobar closes after `kAutoCloseDelay = base::Seconds(5)` (`extension_dev_tools_infobar_delegate.h:30`, `.cc:134-139`). Dismissing it detaches the extension. Nothing a Web Store extension can do removes this infobar.
2. **Native messaging.** Chrome launches the host itself from a JSON manifest, one process per `connectNative` port, kept alive until the port closes. The first argument is the caller's origin. `allowed_origins` takes exact extension ids, no wildcards. A host message can be at most 1 MB, a message to the host at most 64 MiB. The per-user manifest directory is `~/.config/google-chrome/NativeMessagingHosts/` on Linux, `~/Library/Application Support/Google/Chrome/NativeMessagingHosts/` on macOS, and a `HKCU\Software\Google\Chrome\NativeMessagingHosts\<name>` registry key on Windows ([Chrome docs](https://developer.chrome.com/docs/extensions/develop/concepts/native-messaging)). Claude Code's docs say to restart Chrome after the first host install (see below).

## Claude in Chrome (Anthropic)

Closed source. Published manifest and bundle, plus the official docs.

**Manifest** (`manifest.json` in the CRX): MV3, permissions `sidePanel storage activeTab scripting debugger tabGroups tabs alarms notifications webNavigation declarativeNetRequestWithHostAccess offscreen nativeMessaging unlimitedStorage downloads identity favicon`, host permission `<all_urls>`, `externally_connectable` limited to `https://claude.ai/*` and `https://*.claude.ai/*`. Content scripts: `accessibility-tree.js` on `<all_urls>` at `document_start` in all frames, and `cursor-motion.js` plus `agent-visual-indicator.js` on `<all_urls>` in the top frame. Command `Ctrl+E` toggles the side panel.

**1. Action APIs.** A hybrid. `chrome.debugger` drives input and capture. The CDP methods in the bundle are few: `Input.dispatchMouseEvent`, `Input.dispatchKeyEvent`, `Input.insertText`, `Input.cancelDragging`, `Page.captureScreenshot`, `Page.handleJavaScriptDialog`, `Runtime.evaluate`, `Emulation.setFocusEmulationEnabled`, and `Network.*` and `Runtime.consoleAPICalled` for the console and network tools (`assets/mcpPermissions---wcR9fj.js`, **bundle**). The page model comes from the `accessibility-tree.js` content script and `chrome.scripting.executeScript` (13 calls). Tabs and groups use `chrome.tabs` and `chrome.tabGroups` (about 200 calls). The debugger is attached with protocol `"1.3"` per tab and detached by a `detachDebugger` helper, and the attach error text mentions that "DevTools may be open on this tab" (**bundle**). The tool names are `navigate computer read_page find form_input get_page_text javascript_tool tabs_context(_mcp) tabs_create(_mcp) read_console_messages read_network_requests resize_window upload_image file_upload gif_creator shortcuts_list shortcuts_execute update_plan` (**bundle**). So the agent does not speak raw CDP. It calls high-level tools that the extension implements.

**2. Transport.** There are two, both in `assets/service-worker.ts-Bg92QeeM.js` (**bundle**):
- **Native messaging.** The service worker probes two hosts, `com.anthropic.claude_browser_extension` (label "Desktop") and `com.anthropic.claude_code_browser_extension` (label "Claude Code"), with `connectNative`, a `{type:"ping"}` message and a wait for `pong`. Message types include `tool_request`, `tool_response`, `execute_tool`, `mcp_connected`, `mcp_disconnected` and `notification`. Claude Code installs the host manifest itself. On this machine it is `~/.config/google-chrome/NativeMessagingHosts/com.anthropic.claude_code_browser_extension.json`, with `"type": "stdio"`, `allowed_origins` set to `chrome-extension://fcoeoabgfenejglbffodgkkbkcdhcgfn/`, and a `path` pointing to a generated wrapper that runs `exec ~/.local/bin/claude --chrome-native-host` (**observed**). The host process talks to the CLI session over a per-user Unix socket directory, `/tmp/claude-mcp-browser-bridge-<user>/<n>.sock` (**observed**; which side listens is **unverified**). On Windows it uses a named pipe ([docs, Windows-specific issues](https://code.claude.com/docs/en/chrome)).
- **Cloud bridge.** The service worker can also open `wss://bridge.claudeusercontent.com/chrome/<account uuid>` (staging `wss://bridge-staging.claudeusercontent.com`, local dev `ws://localhost:8765`), with a `ping` every 20 s (**bundle**). Claude Code's docs list `bridge.claudeusercontent.com` reachability and a matching claude.ai account and organization as causes of "Browser extension is not connected" and "No browsers are connected" ([docs, Common error messages](https://code.claude.com/docs/en/chrome)). So the extension authenticates as the user's claude.ai account, and Claude Code requires `/login` auth: API keys and `setup-token` turn the integration off. Which transport a given session uses is **unverified**.

**3. What the user sees.** Once: a Web Store install with Chrome's permission prompt, a claude.ai sign-in in the extension ([support article](https://support.claude.com/en/articles/12012173-getting-started-with-claude-in-chrome)), a one-time Claude Code dialog on first `claude --chrome`, and a restart of Chrome if the host is not found on the first try ([docs](https://code.claude.com/docs/en/chrome)). Per run: Claude Code permission prompts that begin `Claude in Chrome wants to`, with an allow-for-this-site-for-the-session option, and the site permissions kept in the extension. Claude's tabs go in their own coloured tab group tied to the session ([docs](https://code.claude.com/docs/en/chrome)). The page overlay draws `claude-agent-glow-border`, a pill reading `Claude is active in this tab group`, and a `Stop Claude` button (`assets/agent-visual-indicator.js-CpmhqLhr.js`, **bundle**). The bundle's "MCP tab group" strings suggest a separate group for MCP-driven sessions (**bundle**, behaviour **unverified**). Because it calls `chrome.debugger.attach` and is a Web Store install, the "Claude started debugging this browser" infobar has to appear while the debugger is attached (Chrome source above). Neither the docs nor the support article mention it.

**4. Install.** Chrome Web Store, Chrome and Edge officially. Claude Code also wires up Brave, Arc, Vivaldi and Opera, but not WSL ([docs](https://code.claude.com/docs/en/chrome)). The CLI writes the host manifest for every detected browser.

## Codex Chrome extension (OpenAI)

Closed source. The Web Store listing for the Codex extension id now serves an extension named "ChatGPT" ("Control your browser with ChatGPT."). Sources are the published manifest and bundle, the Codex `chrome` plugin the Codex app installed on this machine, OpenAI's docs, and public issues.

**Manifest** (`manifest.json` in the CRX): MV3, permissions `alarms bookmarks debugger declarativeNetRequestWithHostAccess downloads favicon history nativeMessaging notifications offscreen scripting sessions storage tabGroups tabs topSites webNavigation contextMenus sidePanel`, optional `downloads.open`, host permission `<all_urls>`. Content scripts run only on `https://chatgpt.com/*`, so nothing is injected into ordinary pages at load. A side panel (`codex-work-sidepanel.html`) hosts the side chat.

**1. Action APIs.** CDP, for nearly every action, through `chrome.debugger`, which is the heaviest use of the five. The bundle sends a full Playwright-like set: `Page.getFrameTree`, `Page.createIsolatedWorld`, `Runtime.evaluate`, `Runtime.callFunctionOn`, `DOM.describeNode`, `DOM.getBoxModel`, `DOM.getContentQuads`, `Input.dispatchMouseEvent`, `Input.dispatchKeyEvent`, `Target.setAutoAttach`, `Page.setInterceptFileChooserDialog`, `Page.screencastFrame` and more (`background.js`, **bundle**). A generic handler forwards `{method, target, commandParams}` to `chrome.debugger.sendCommand`, and answers `Target.getTargets` from `chrome.debugger.getTargets()` (**bundle**). That is a CDP relay much like Playwright's. There are also 21 `chrome.scripting.executeScript` calls and wide `chrome.tabs` use. The plugin's agent docs say actions run as "Playwright, screenshots, CUA, and content reads" on a claimed `Tab` (`docs/tab-claiming-chrome.md:8`, **observed**).

**2. Transport.** Native messaging. `background.js` calls `chrome.runtime.connectNative(this.application)`, falls back between host names `com.openai.codexextension`, `.dev` and `.internal`, and reconnects on an alarm (**bundle**). The Codex app's `chrome` plugin installs the host. On this machine, `~/.config/google-chrome/NativeMessagingHosts/com.openai.codexextension.json` is `"type": "stdio"`, its `allowed_origins` lists the Chrome id and the Edge id `odlomjlbamekndcpllcnffbgeohgkmjh`, and its `path` points to a native binary at `~/.codex/plugins/cache/openai-bundled/chrome/latest/extension-host/linux/x64/extension-host` (**observed**). The plugin's `scripts/extension-ids.json` lists the manifest directories for Chrome, Chromium, Edge, Brave, Opera and Vivaldi on each OS, and on Windows a manifest under `AppData/Local/OpenAI/extension` registered at `HKCU\Software\Google\Chrome\NativeMessagingHosts` (**observed**). The host reaches the Codex app over Unix sockets in `/tmp/codex-browser-use/<uuid>.sock`: the string is in the host binary, a live socket is present, and [openai/codex#21719](https://github.com/openai/codex/issues/21719) describes a mismatch between the host's socket and the app's socket. No cloud relay was found.

**3. What the user sees.** Once: open the desktop app's Computer Use settings, pick a browser, let it install the plugin, install the extension, and accept Chrome's permission prompt, which includes "Access the page debugger", "Read and change all your data on all websites" and "View and manage your tab groups". The browser then shows "Manage" ([OpenAI docs](https://learn.chatgpt.com/docs/chrome-extension.md)). Per run: "By default, ChatGPT asks before it interacts with each new website", with Allow once, Allow for this site, Allow for all sites or Decline (same page). Agent tabs go in a managed tab group with a random colour and a session title, set by `browser.nameSession("...")` (`docs/session-naming.md`, **observed**; `createGroup` and `chrome.tabGroups.update({color, title})` in `background.js`, **bundle**). Claiming an existing user tab does not move it into the group (`docs/tab-claiming-chrome.md:8`). Agent tabs close at the end of the turn unless marked (`docs/tab-cleanup-chrome.md`). Work runs in the background by default (`docs/visibility.md`). The debugger infobar follows from the Chrome source above. The docs do not mention it.

**4. Install.** Chrome Web Store (Edge Add-ons for Edge), started from the Codex or ChatGPT desktop app, which installs the host binary and manifest. macOS and Windows at launch; Linux works on this machine (**observed**). Public issues show the weak spot is a desync between host and app, not the install: [#21705](https://github.com/openai/codex/issues/21705) and [#21879](https://github.com/openai/codex/issues/21879) report the handshake timing out even though every diagnostic passes.

## Playwright MCP `--extension` (Microsoft)

Open source. The extension now lives at `microsoft/playwright/packages/extension`, and the relay at `packages/playwright-core/src/tools/mcp/`. The `playwright-mcp` README points there (`README.md:511-513`).

**Manifest** (`packages/extension/manifest.json:6-14,34`): MV3, permissions `debugger activeTab tabs tabGroups`, host `<all_urls>`, a service worker, and a pinned `key` so the id is always `mmlmfjhmonkocbjadbfplnigmagldckm` (`utils/extension.ts:20-21`). It has no content scripts and no `nativeMessaging`.

**1. Action APIs.** A pure CDP relay. The extension runs whatever the relay asks from an allowlist, `chrome.debugger.attach/detach/sendCommand` and `chrome.tabs.create/remove`, and forwards `chrome.debugger.onEvent/onDetach` and `chrome.tabs.onCreated/onRemoved` for attached tabs (`src/relayConnection.ts:41-55`). On the server, `BrowserModel` translates `Target.*` and `Browser.*` into those calls, so Playwright's `connectOverCDP` thinks it is talking to a normal browser (`cdpRelay.ts:17-62`). Tab ownership is a Chrome tab group per client (`src/connectedTabGroup.ts`). Dragging a tab into the group attaches it, and dragging it out detaches it (`relayConnection.ts` `attachTab`/`detachTab`).

**2. Transport.** A loopback WebSocket that the extension dials out to. No native host. The MCP server opens a `WSServer` on an ephemeral port bound to `localhost` (`cdpRelay.ts:145`, `utils/wsServer.ts:69`), with two random paths, `/cdp/<uuid>` for Playwright and `/extension/<uuid>` for the extension (`cdpRelay.ts:120-122`). To hand the extension that URL, the server **spawns the Chrome executable** with `chrome-extension://<id>/connect.html?mcpRelayUrl=ws://...&protocolVersion=...&token=...` as an argument (`cdpRelay.ts:170-218`). When Chrome is already running, the new process passes the URL to the running browser, which opens it as a tab in the existing profile. The extension page accepts only `127.0.0.1` or `[::1]` relay hosts (`src/ui/connect.tsx:62-65`). The service worker opens the WebSocket only after approval (`src/pendingConnection.ts`). The connect page pings the service worker every 20 s to keep it alive (`src/background.ts:97-100`). The server finds the profile by reading `Local State` `profile.last_used` and looking for `Extensions/<id>` or a settings record in `Preferences` (`utils/extension.ts:25-79`).

**3. What the user sees.** Once: a Web Store install. Optionally, copy `PLAYWRIGHT_MCP_EXTENSION_TOKEN` from the extension's status page into the MCP config (`packages/extension/README.md:47-74`). Per run, without a token: a connect tab opens and the user picks a tab and clicks Allow (README lines 37-39). With a token matching `getOrCreateAuthToken()` it connects without asking (`connect.tsx:98-108`). With `--background` and a token, Chrome is passed `--open-in-background` so the window does not take focus (`cdpRelay.ts:208-210`, README line 78). Each client gets a tab group titled `Playwright · <client>` in a distinct colour (`connectedTabGroup.ts:19-46`), and controlled tabs get a green check badge (`connectedTabGroup.ts:24`). The debugger infobar `"Playwright Extension" started debugging this browser` is not mentioned in the README, but follows from the Chrome source.

**4. Install.** [Chrome Web Store](https://chromewebstore.google.com/detail/playwright-extension/mmlmfjhmonkocbjadbfplnigmagldckm). The pinned `key` also lets an unpacked build keep the same id, so the server's id check works either way.

## browser-use

Open source. **No extension.** None of `browser-use`, `browser-harness`, `browsercode` and `desktop` contains a `chrome.debugger`, `connectNative` or `NativeMessagingHosts` reference (grep at the revisions above).

- **Library.** `Browser.from_system_chrome()` (`browser_use/browser/session.py:446`) finds the system Chrome and profile, then `_copy_profile` copies the profile and `Local State` into a temporary `browser-use-user-data-dir-*` (`browser_use/browser/profile.py:849-903`). The copy runs Chrome with `--remote-debugging-port`, because Chrome will not allow remote debugging on the default user data dir (assert at `watchdogs/local_browser_watchdog.py:118-120`). Its docs tell the user to quit Chrome entirely before running (`skills/open-source/references/browser.md:173-185`). The user gets their cookies but not their live browser.
- **browser-harness / CLI.** This one attaches to the user's running Chrome through `chrome://inspect/#remote-debugging`. It reads `DevToolsActivePort` (`src/browser_harness/daemon.py:124-175`) and opens that page if the toggle is off. On macOS, `browser-harness mac-approve` clicks Chrome's "Allow remote debugging?" sheet through AppleScript `AXPress`, which needs the Accessibility permission (`src/browser_harness/macos.py:17-37,72-118`, and `skills/browser-use/SKILL.md:115-147,283-284` in `browser-use`). That is the same dialog fastbrowse hits in #630. browser-use automates the click rather than avoiding the dialog. Linux and Windows have no helper (`SKILL.md:147`).
- **Cloud.** The alternative it recommends is a hosted Browser Use Cloud browser (`skills/remote-browser`).

## Stagehand / Browserbase

Open source. There is a Chrome extension, but it is a **runtime that executes inside a browser Stagehand already reaches over CDP**. It is not a way into a user's Chrome.

**Manifest** (`packages/extension/manifest.json`): "Stagehand Runtime", MV3, `minimum_chrome_version` 137, permissions `debugger offscreen scripting tabs declarativeNetRequest`, host `<all_urls>`, and an `<all_urls>` content script at `document_start` in all frames and `about:blank`, in the ISOLATED world.

**1. Action APIs.** The Stagehand runtime (`understudy/`) runs in the service worker. It opens a WebSocket to the browser's CDP URL itself (`understudy/browserWebSocketTransport.ts`, `service-worker.ts:42-63`), uses `chrome.debugger.getTargets` for tab mapping (`understudy/chromeTabs.ts:46-51`), `chrome.declarativeNetRequest` for domain policy, and the content script as a locator runtime.

**2. Transport.** The SDK holds a CDP WebSocket to the browser, loads the extension with `Extensions.loadUnpacked` or finds it with `Extensions.getExtensions`, attaches to the extension's service-worker target, and installs `Runtime.addBinding("__stagehandSendToHost")`. It then exchanges JSON-RPC through `Runtime.evaluate("globalThis.__stagehandReceiveFromHost(...)")` (`packages/sdk-ts/src/cdpClient.ts:380-430,945-964`; binding name at `packages/protocol/schema-registry.ts:129`). On Browserbase, the extension zip is uploaded through `browserbase.extensions.create` and attached to the session (`packages/sdk-ts/src/browserbaseExtension.ts`). Locally, Stagehand launches its own Chrome with `--remote-debugging-port`, `--enable-unsafe-extension-debugging` and a temporary `--user-data-dir` (`packages/sdk-ts/src/browser/localBrowser.ts:40,173-203`).

**3 and 4. User-facing.** Nothing for the user to see or install. It is either a cloud session or a throwaway local Chrome. Its README sells the extension for latency ("Stagehand runs as an extension next to the browser", `README.md:304`).

**Related: Browserbase ModCDP** (`browserbase/ModCDP`) is closer to what #630 needs. Its "ModCDP Bridge" extension (`extension/manifest.json`: `activeTab tabs debugger offscreen nativeMessaging`, pinned `key`) serves a CDP endpoint to Playwright, Puppeteer or Stagehand over one of four upstreams: a direct WebSocket, a pipe, **native messaging** through host `com.modcdp.bridge` (`README.md:147`, `js/src/transport/NativeMessagingDownstreamTransport.ts:12,143-155`), or **reverse WebSocket**, where the extension auto-dials `ws://127.0.0.1:29292` and a local proxy serves a normal CDP endpoint (`README.md:149-162`). The service worker can route commands to `chrome.debugger` (`README.md:267-284`). Its own notes say using stock Chrome's default profile still goes through `chrome://inspect` and "accepting Chrome's connection prompt" (`README.md:219,498`), so its debugger-route modes are the ones that skip the dialog.

## Implications for fastbrowse

1. **Both shipping products avoid the remote-debugging dialog by doing what #630 proposes**: a Web Store MV3 extension with `debugger`, `tabs`, `tabGroups`, `scripting` and `nativeMessaging`, plus a stdio native host that the agent's own installer registers. Codex's host is a native binary that bridges to a Unix socket owned by the app. That fits a Rust `fastbrowse` binary acting as its own host (`fastbrowse --native-host`, the way Claude Code runs `claude --chrome-native-host`).
2. **Zero prompts is not reachable with a Web Store install.** Chrome shows `"<name>" started debugging this browser` on every `chrome.debugger` attach, and only policy installs or `--silent-debugger-extension-api` suppress it (`debugger_api.cc:722-726`). Claude and Codex live with it. It is an infobar, not a modal, so a run does not block on it. Keep the debugger attached for the whole run and detach at the end to get one infobar per run instead of one per action. Enterprise users could force-install by policy to remove it.
3. **Relay raw CDP, as Codex and Playwright do.** fastbrowse already speaks CDP. The extension can be a thin allowlisted forwarder (`attach`, `detach`, `sendCommand`, `getTargets`, `tabs.create/remove`, events), and the Rust side can emulate the browser-level `Target.*` calls that `chrome.debugger` refuses. Playwright's `BrowserModel` (`cdpRelay.ts:17-62`) is the reference for that translation. [`extension-cdp-coverage.md`](extension-cdp-coverage.md) lists what has to move.
4. **Pick the transport.** Native messaging needs no open port and gets Chrome-verified caller identity (`allowed_origins` plus the origin argument), but it caps host-to-extension messages at 1 MB (screenshots flow the other way, under the 64 MiB limit, so this limits large script payloads). It also needs an installer step per browser and OS, plus a local socket from the host to the running `fastbrowse` process, and Codex's open issues show that hand-off is where it breaks. Playwright's loopback WebSocket needs no host manifest: it launches the Chrome binary with a `chrome-extension://` URL to hand over a random-path `ws://localhost` URL and a token. That is simpler to ship from a CLI and works with unpacked builds, but it opens a tab per run and depends on a loopback check in the extension. A defensible plan: native messaging as the main path, matching both shipping products, with the Playwright launch-a-URL handshake as the fallback when no host is registered.
5. **Copy the UX that works.** Use a per-run tab group named after the task, with its own colour, as the ownership boundary (all three extensions do this). Put agent tabs in the background by default (Codex, Playwright `--background`). Add a visible Stop control in the page (Claude). Close agent tabs at the end of a run unless they are kept (Codex). Pin the extension id with a manifest `key` so dev builds and Web Store builds share `allowed_origins` (Playwright, ModCDP).
6. **Do not follow browser-use.** Its live-browser path is the `chrome://inspect` dialog plus a macOS-only AppleScript clicker, and its library path copies the profile into a second browser. Neither meets #630's bar.
7. **Expect restricted-frame detaches.** Playwright's troubleshooting notes that a frame from another extension makes Chrome detach the debugger (`packages/extension/README.md:102-104`). Users' own Chromes have many extensions, so the run has to recover from `onDetach` with reason `target_closed`, as Playwright's reattach logic does (`relayConnection.ts` `_maybeScheduleReattach`), and report a clear error when the tab cannot be attached.
