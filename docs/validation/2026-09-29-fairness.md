## Confirmed defects

- Fastbrowse: HTTP error addresses were included in visited evidence. The verifier explicitly accepted historical visits for a final navigation outcome. After recovery went Back, six selected runs falsely reported complete on the homepage. The external grader caught them.
- Harness: an Ultrafast browser IPC timeout at the correct Wikipedia URL was counted as an agent failure. Browser transport classification needs a symmetric, bounded retry rule before the next run.
- Harness: the Ultrafast cap counts model decisions, while Fastbrowse does not charge stale attempts to its action budget. Two executed arXiv actions consumed its 50-decision cap. The limits and units need correction and disclosure.
- Evidence: a matching final URL does not prove a successful HTTP document. The old final-page capture omits response status and content; neither arm's old navigation passes can exclude an HTTP error page from the retained rows alone.

## Recorded diagnostics

- Ultrafast arXiv: the recorded diagnostic made 100 decisions and two actions. Decisions 3-100 chose the background Search button while the search overlay was open. Every rejected action reported `StalePage: Target changed or is covered. Observe again.` The upstream snapshot includes obscured controls, its executor refuses them, and its action set has no Enter operation. The recording confirms the overlay says to press Enter. This is an upstream control-selection/recovery limitation, not an HTTP outage (final document HTTP 200).
- Ultrafast flights: the recorded diagnostic reached 50 executed actions. With Stops open, each decision saw only Close dialog, scroll and wait. The video visibly shows Nonstop only. An independent browser probe using the pinned upstream Browser confirmed all four native radio inputs have CSS opacity 0; upstream snapshot.js filters them out with checkVisibility(checkOpacity=true) and does not substitute their visible wrappers. The final HTTP 200 search URL independently confirms that the nonstop filter was never applied.
- HN HTTP 419 origin: traces establish the status, not whether it came from the site or a browser/proxy intermediary. Do not describe it as provider slowness or proven anti-bot blocking.

## Fixes and validation

- Fastbrowse verification now distinguishes a requested final destination from an intermediate visit. HTTP errors are removed from visited evidence, action effects retain their status, and a fresh final error document cannot complete.
- The original start address is retained independently of completion evidence for navigation reports.
- Ultrafast now has 50 executed actions and 100 decisions, within its upstream 60-action/120-decision safety limits. Stale choices no longer spend its action allowance.
- Both observed arms retain final document status, title and text. Navigation passes require a successful, nonempty document as well as a matching destination. Publication rejects navigation passes missing that evidence.
- Browser IPC/CDP timeouts have one retry, with the failure class retained. Observed final HTTP 408/419/429/5xx documents use the bounded site-outage retry rule for either arm.
- Independent site probes remain diagnostic; a slow or failed host-side probe no longer discards an otherwise completed browser run.
- Every attempt, retry wait and reported cost remains in the ledger. Completed slow runs retain their actual time and cost.
- Development suite: 39/39. Heldout before this fix: 27/27; after: 27/27. No tuning to heldout outcomes. The core navigation suite has been used for diagnosis and is not a heldout estimate.

## Second validation round

## Browser setup correction

The candidate from clean `8861b3a` was stopped after source review found an explicit viewport override in
Ultrafast but none in Fastbrowse. That was a setup concern, not proof of different rendered dimensions.
The [partial candidate ledger](2026-09-29-ultrafast-ready-ten.attempts.jsonl) retains 79 physical attempts,
71 selected. Interrupted in-flight calls may have incurred costs absent from the partial ledger.

The next candidate, `dc19593`, added the same CDP override and recorded actual dimensions. Its
[first 11 attempts](2026-09-29-ultrafast-matched-ten.attempts.jsonl) showed varying sizes in both arms, so
it too was stopped. The source-level override was not taking effect in either cloud browser.

A [cloud probe with resizing disabled](2026-09-29-cloud-resizing-disabled.json) established that both
JavaScript and CDP layout metrics remain unchanged after the override. Browser Use's
[V3 request schema](https://api.browser-use.com/api/v3/openapi.json) documents `allowResizing`, default false.
A [probe with resizing enabled](2026-09-29-cloud-resizing-enabled.json) then measured 1120 by 780 CSS pixels
and device scale 1, confirmed by CSS media queries. The reported scale has floating-point noise. Two [pinned Ultrafast browser probes](2026-09-29-ultrafast-resizing-enabled.json) independently produced the same CSS dimensions and scale, without model calls.

Both navigation arms now opt into cloud resizing. Fastbrowse applies the same override as pinned Ultrafast;
Ultrafast's browser code stays unchanged. Actual dimensions are retained, and publication rejects missing
or different dimensions on scored rows, allowing only numerical scale rounding. This changes the cloud
configuration for both arms; the service warns that resizing can reduce stealth. Ordinary Fastbrowse runs
keep the cloud default. The next comparison starts from a clean commit, with new navigation task versions.
Earlier batches are never pooled into it. The browser regression passes locally; cloud probes establish
that the required cloud option makes the same override effective there.

The `acc57d1` candidate was also stopped: its [12 physical attempts](2026-09-29-ultrafast-resizable-ten.attempts.jsonl)
exposed a final-observation timing mismatch. Ultrafast's parent read the tab after the browser daemon
had disconnected. A [before/after probe](2026-09-29-cloud-disconnect.json) measured device scale 1 before
cleanup and 1.25 or 2 afterward. The grader now captures the run's final page before that cleanup, as
Fastbrowse does. Both use the same observation scripts. Tests cover capture ordering, evidence propagation
and restoring hidden controls after a snapshot error. This changes the observation seam, not Ultrafast's
policy or offered actions. A two-arm cloud preflight precedes the next full comparison.

## Scope and limits

This compares product configurations, not matched helper models. Both use Jev through OpenRouter, but Fastbrowse can use its configured backup; Ultrafast keeps its native helper and retry behavior. Fastbrowse can propose a URL shortcut; Ultrafast chooses from page controls. These are product capabilities and must be stated, not described as a controlled model comparison. Six shared navigation tasks cannot establish general workflow superiority.

The old 127 attempts remain unchanged as diagnostic evidence. They are not pooled with the new run. The earlier unmerged 0.5.13 batch is archived as diagnostic evidence rather than published results.
Historical releases already on main retain their old protocol; the corrected task versions must not be compared as if the grading had stayed fixed.
